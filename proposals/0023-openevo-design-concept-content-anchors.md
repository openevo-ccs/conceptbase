# RFC-0023: Migrate OpenEvo's 9 content anchors into a governed `OPENEVO-DESIGN-CONCEPT` vocabulary

**Type:** `content`

**Status:** `proposed`
**Author(s):** OpenEvo ConceptBase maintainers (drafted by lab-manager, per `lab_manager/docs/design-notes/open-decisions-register.md`'s "Actionable now" list and `openevo-graph/docs/design-notes/cleanup-development-integration-recommendations.md` §2)
**Date:** 2026-09-15 (corrected same day — see "Proposed change"'s relatedAnchors note and "Prior draft" below)

## Motivation

OpenEvo's educational design concept rests on three pillars: 3 design principles, 9 content anchors, and 6 thinking tools. The 9 content anchors (Ancient Ancestors, Cross-species Comparisons, Child Development, Cooperation Games, Cultural Diversity, Governing the Commons, Our Mind, Computer Models, Global Sustainability Goals) have real, substantial content — full descriptions, K-2 through 13-16 grade-band progressions, CASE standards links, cross-anchor relations — but only ever existed as hand-authored JSON in `openevo-graph/nodes/content_anchors.json`, with no ConceptBase presence at all. `content-anchor-mapper`, `thinking-tools-kit`, and `design-concept-coach` (three of this ecosystem's own skills/agents) already depend on this vocabulary informally, and `teachers-guide`'s 2026-09-03 audit independently hit the exact same gap trying to write its own "Educational Design Concept" chapter — this is a live, confirmed blocker, not a hypothetical one.

This RFC was first scoped in `lab_manager/docs/design-notes/openevo-graph-and-ccs-graph-design-governance-concept.md` (2026-07-22, §9.1-9.2) as a joint `oe:ContentAnchor`/`oe:ThinkingTool` migration. That scope has narrowed since: `openevo-graph/docs/design-notes/cleanup-development-integration-recommendations.md` (2026-09-03) confirmed neither anchor needs a new ontology class — both fit the tagged-`oe:Concept` pattern RFC-0012 already established for eva4k12's cross-cutting themes. More importantly, the "thinking tool" half of the original scope turned out to already be resolved by different means: `methodsbase/records/methods.yaml` gained 6 real `OE-METHOD-*` records for exactly the 6 OpenEvo thinking tools (Tinbergen's Questions, Causal Mapping, Payoff Matrices, the Noticing Tool, Analogy Mapping, Structure of Knowledge Diagrams) on 2026-09-02, each with a full description, primary sources, and provenance tracing back to the Teacher's Guide — governed, real, and already in MethodsBase. This RFC therefore covers **content anchors only**; thinking tools need no further action here.

## Proposed change

**New vocabulary: `vocabularies/OPENEVO-DESIGN-CONCEPT-v1.0.0.yaml`**, 9 `oe:Concept` entries, ids minted directly via the post-2026-08-16 slug scheme (`OE-CONCEPT-openevo-design-concept-<anchor-slug>`, e.g. `OE-CONCEPT-openevo-design-concept-ancient-ancestors`) — no numeric ID block reservation needed (see "ID block reservation" below).

All 9 anchors are genuinely new to ConceptBase — none duplicate an existing entry (checked directly: no existing vocabulary has a matching label or close synonym for any of the 9).

Field mapping, generated by `scripts/migrate_content_anchors.py` from the source JSON rather than hand-transcribed, given the volume (9 anchors × 5 grade bands + relations + tags):

| Source field (`content_anchors.json`) | ConceptBase field |
|---|---|
| `label` | `labels.en` |
| `coreIdea` (the concise 1-2 sentence claim) | `definitions.en.general` |
| `desc` (the fuller descriptive paragraph) | `extensions["oe:fullDescription"]` — no schema field fits a paragraph-length description; carried losslessly rather than dropped or lossily compressed into `definitions` |
| `discipline` | `extensions["oe:discipline"]` |
| `subjectAreas` | `extensions["oe:subjectAreas"]` |
| `gradeProgression` (K-2 through 13-16) | `extensions["oe:developmentalArc"]` — same field name and pattern RFC-0012 established for eva4k12's developmental-arc content, which has the identical no-schema-field problem |
| `tags` | `extensions["oe:tags"]` |
| `note` (curatorial note) | `extensions["oe:curatorNote"]` |
| `relatedAnchors` | `relations.skos:related` |
| `id`, `x`, `y`, `type`, `gradeBands`, `linkedNodes`, `caseLinks`, `lessonIdeas` | Not migrated — see "Deferred" |

Every entry is tagged `extensions["oe:conceptRole"] = "content-anchor"` so tooling can distinguish this vocabulary's entries from ordinary concepts without a schema change — the identical mechanism and field name RFC-0012 used for eva4k12's cross-cutting themes, not a new pattern invented for this RFC.

**`relatedAnchors` is carried through exactly as authored, corrected same day.** The source data is asymmetric in 7 of the resulting 21 relation pairs (e.g. Ancient Ancestors lists Our Mind as related, but Our Mind's own list doesn't list Ancient Ancestors back). A first pass of this RFC read that as an authoring gap and had the migration script auto-add the 7 missing reciprocal edges, on the reasoning that `skos:related` is symmetric by definition (SKOS spec). That was wrong: every one of the 9 source anchors lists **exactly 3** `relatedAnchors`, no more and no fewer — checked directly, not assumed — which is a strong, consistent signal of a deliberate curated "top 3" per anchor, not an oversight. Forcing symmetry would have silently pushed 7 of the 9 anchors to 4 relations each, overriding that curation. The migration now preserves the source's one-directional relations as-is; `scripts/check_related_symmetry.py` correctly reports this vocabulary as asymmetric, and that's accepted, not a defect — the check is advisory only (it is not run in CI; see `.github/workflows/validate.yml`).

Once accepted, `openevo-graph/nodes/content_anchors.json` should become a generated mirror of this vocabulary (a script reading the ConceptBase registry) rather than hand-maintained data — this is the second of two ungoverned-data-source risks the 2026-07-22 design note originally flagged (the first, thinking tools, already resolved itself via MethodsBase). Not built as part of this RFC; a natural immediate follow-up once this merges.

## Deferred to a follow-up RFC (not resolved here)

- **CASE-standards crosswalk** (`caseLinks` — 34 total alignment notes across the 9 anchors, referencing NGSS, C3, IB MYP, CCSS-Math, CCSS-ELA, P21, CSTA, AP CSP, UN SDGs, OECD Learning Compass). This has no ConceptBase home yet (Phase 2 alignments, per `common.defs.yaml`'s own `alignmentConceptRef`/`vocabRef` machinery being built for exactly this but not yet populated for any vocabulary). Per `cleanup-development-integration-recommendations.md` §2: "stays a separate, later step — it has no ConceptBase home yet and shouldn't be gated behind this migration."
- **`linkedNodes`** (a superset of `relatedAnchors` — every anchor's `linkedNodes` list is `relatedAnchors` plus 1-3 more): not migrated as a second relation type. `relatedAnchors` already captures the curated, intentional cross-anchor relationships; `linkedNodes` looks like a broader graph-layout/rendering concern (the field sits alongside `x`/`y` coordinates in the source) rather than a second, distinct SKOS-worthy claim. Worth a second look if `openevo-graph`'s own maintainers disagree with that reading.
- **Once `openevo-graph/nodes/content_anchors.json` becomes a generated mirror** (see "Proposed change" above) — a real follow-up, not started here.
- **`teachers-guide`'s `{{contentAnchor: ...}}` shortcode**, resolving against ConceptBase instead of `openevo-graph` directly (`scripts/lookup.py`) — the actual unblock for `teachers-guide`'s stuck Educational Design Concept chapter, per `cleanup-development-integration-recommendations.md` §2 item 3. Depends on this RFC merging first.

## Relations

- Uses `oe:Concept` (RFC-0002) exclusively — no schema changes, same "don't invent machinery you don't need" finding RFC-0012 reached for eva4k12's cross-cutting themes.
- All 9 entries relate only to each other (`relations.skos:related`, one-directional where the source is one-directional — see "Proposed change") — no cross-vocabulary relations asserted here. Whether any content anchor should `skos:related` an existing `BIO-CORE`/`OE-INTERDISCIPLINARY`/`EVA4K12-CONCEPTS` entry (e.g. Ancient Ancestors and eva4k12's own Pattern/Scale concepts) is a real question, left for a future alignment pass rather than asserted unilaterally here.
- Complements (does not compete with) the 6 `OE-METHOD-*` thinking-tool records already in MethodsBase — several of those records' own `contributor_notes` already reference "the Guide's nine content anchors" informally; once this RFC merges, that reference could become a real cross-repo id link, itself a small follow-up.

## Standards justification

Direct, unmodified use of `oe:Concept` (RFC-0002) and its existing `extensions` field, following RFC-0012's precedent exactly. The one structural question — whether content anchors need a new `oe:ContentAnchor` ontology class — is answered "no" for the same reason RFC-0012 gave for cross-cutting themes: nothing this ecosystem's tooling needs (validation, registry building, relation traversal) actually depends on content anchors being a distinct type; `extensions["oe:conceptRole"]` is sufficient, keeping this a `content` RFC rather than a `specification-amendment`.

## ID block reservation

Not applicable — `oe:Concept` ids for new vocabularies are minted directly from the vocabulary's own slug (`OE-CONCEPT-<vocab-slug>-<code-slug>`) since the 2026-08-16 supersession of numeric block allocation (`GOVERNANCE.md`, "Identifier Block Allocation" → "Concept ID blocks"). No `GOVERNANCE.md` table edit is needed for this RFC.

## Prior draft — a real RFC-number collision, found and reconciled same day

A second, independent draft of this exact migration already existed, unmerged, since 2026-09-04 (`rfc-0023-content-anchor-vocabulary-migration`, also number 0023) — an earlier Claude session reached the same "content anchors only, thinking tools already in MethodsBase" conclusion 11 days before this draft did, but its ledger claim was never pushed to `main` (`RFC_LEDGER.md`'s own note on that branch: "`main`'s working tree had large unrelated in-flight uncommitted work at claim time... that this deliberately avoided touching or entangling with"), so today's draft claimed the same number again without any collision warning. Found via an independent review pass, not self-caught.

The two drafts differ in one substantive way: the older draft's own vocabulary carries less of the source content forward (no `oe:fullDescription`, `oe:tags`, or `oe:curatorNote`) while its meta description claims `openevo-graph`'s original file would "retain the fuller field set" as a generated mirror of this vocabulary — a real inconsistency, since a mechanically generated mirror can't independently retain data absent from the thing generating it. This draft is more complete and doesn't have that inconsistency, so it supersedes the older one; the older branch should be closed without merging once this RFC is reviewed, and `RFC_LEDGER.md` corrected to show one 0023 entry, not a race between two.
