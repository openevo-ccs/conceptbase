# RFC-0023: Migrate `openevo-graph`'s 9 Content Anchors into a governed `OPENEVO-CONTENT-ANCHORS` vocabulary

**Type:** `content`

**Status:** `proposed`
**Author(s):** OpenEvo ConceptBase maintainers (drafted in support of `openevo-graph`'s consolidation plan — see `lab_manager/docs/design-notes/openevo-graph-and-ccs-graph-design-governance-concept.md` §9.1 and `openevo-graph/docs/design-notes/cleanup-development-integration-recommendations.md` §2)
**Date:** 2026-09-04

## Motivation

`openevo-graph/nodes/content_anchors.json` holds the only structured, machine-readable
representation anywhere in this ecosystem of OpenEvo's own 9-anchor design-concept vocabulary
(Ancient Ancestors, Cross-species Comparisons, Child Development, Cooperation Games, Cultural
Diversity, Governing the Commons, Our Mind, Computer Models, Global Sustainability Goals) — the
bedrock content organizing `content-anchor-mapper`, `design-concept-coach`,
`curriculum-architect`, and `dbr-cycle-facilitator`'s work, and now (as of `teachers-guide`'s
2026-09-03 content audit) driving `teachers-guide`'s own `contentAnchor` manifest field directly,
informally, with no governed id to cite. This has sat as an explicitly-planned "next step" since
2026-07-22 (the design note above, §9.1) without being executed — the sequencing condition that
deferred it (behind `eva4k12`'s migration) resolved 2026-08-04, so nothing currently blocks it.

**Correction to the original 2026-07-22 plan, found while drafting this RFC:** that plan proposed
migrating *both* content anchors and thinking tools together. Checking MethodsBase directly before
drafting found all 6 thinking tools already exist as real, complete `OE-METHOD-*` records
(`OE-METHOD-tinbergens-questions`, `-causal-mapping`, `-payoff-matrices`, `-noticing-tool`,
`-analogy-mapping`, `-structure-of-knowledge-diagrams`) — already embedded in `teachers-guide`'s
Thinking Tools chapter. Thinking tools are therefore **already governed and out of scope for this
RFC**; `openevo-graph/nodes/thinking_tools.json` should be flagged as legacy (a candidate to become
a generated mirror of MethodsBase, or simply retired) in a follow-up, not folded into this
migration.

This RFC deliberately does not invent new ontology machinery: consistent with the RFC-0012
precedent for eva4k12's cross-cutting themes, content anchors are a tagging concern on top of
`oe:Concept`, not a distinct type — see "Standards justification" below.

## Proposed change

**New vocabulary: `vocabularies/OPENEVO-CONTENT-ANCHORS-v1.0.0.yaml`**, 9 `oe:Concept` entries,
ids `OE-CONCEPT-openevo-content-anchors-<slug>` (direct-mint slug scheme, per the 2026-08-16 id
migration — no numeric block reservation).

Generated by `scripts/migrate_content_anchors.py` (this RFC) reading
`openevo-graph/nodes/content_anchors.json` directly, given the volume (9 anchors × 5 grade bands)
and to avoid transcription error, matching RFC-0012's own script-driven approach. Output validated
clean against `scripts/validate.py` and `scripts/check_related_symmetry.py` (61 concepts across 6
vocabularies, all symmetric) — see "Files affected."

**Only the governed subset migrates**, deliberately narrower than the source file:

| Source field | Destination |
|---|---|
| `id`, `label` | `id` (as `OE-CONCEPT-openevo-content-anchors-<id>`), `labels.en` |
| `coreIdea` | `definitions.en.general` (a concise synthesis, per the same approach RFC-0012 used) |
| `gradeProgression` | `extensions["oe:developmentalArc"]`, keyed by grade band — no schema home for developmental-arc content, same extension key RFC-0012 established |
| `relatedAnchors` | `relations.skos:related` — **symmetrized**. The source field is each node's own curated "top 3 most related" list, not a symmetric relation (7 of the original 27 edges were one-directional); `scripts/check_related_symmetry.py` requires symmetry, so the migration script unions each pair's edge in both directions rather than silently dropping the asymmetric half. |
| `id` (again) | `extensions["oe:openevoGraphSourceId"]` — provenance pointer back to the source node, same pattern as RFC-0012's `oe:eva4k12SourceURI` |
| new | `extensions["oe:conceptRole"]: "content-anchor"` — the same tagging mechanism `"cross-cutting-theme"` already uses for `EVA4K12-CONCEPTS`, so tooling can filter this subset without a schema change |

**Deliberately NOT migrated** — these stay local to `openevo-graph`'s own generated mirror, which
retains the full original field set: `discipline`, `subjectAreas`, `tags`, `caseLinks` (the CASE
standards crosswalk — has no ConceptBase home yet, Phase 3/4 scope, a separate future RFC per the
design note's §9.5 sequencing), `lessonIdeas`, `note`, and the graph-layout `x`/`y` coordinates.
Duplicating these into ConceptBase would recreate the "two ungoverned data sources" problem this
migration exists to fix.

**Post-merge**, per the design note's §9.3: `openevo-graph/nodes/content_anchors.json` becomes a
generated mirror of this vocabulary (a script reading the ConceptBase registry, analogous to
`conceptbase/scripts/build_registry.py`'s own output pattern) rather than continuing as
hand-maintained duplicate data — not executed as part of this RFC, since it's a change to another
repo and belongs in its own follow-up once this RFC is accepted.

## Deferred to a follow-up (not resolved here)

- **`openevo-graph/nodes/thinking_tools.json`'s legacy status** — see "Correction" above. A
  follow-up should either retire the file (MethodsBase is now the real source of truth) or
  regenerate it as a mirror of the 6 `OE-METHOD-*` records, and update
  `openevo-graph/CONTRIBUTING.md`/`GOVERNANCE.md` accordingly (currently still describe thinking
  tools as pending migration, which this RFC's finding corrects).
- **`teachers-guide` shortcode wiring** — once this RFC is accepted, `teachers-guide/scripts/lookup.py`
  should gain a `{{contentAnchor: ...}}` shortcode type resolving against this vocabulary, so its
  Educational Design Concept / Learning Goals chapter (currently stuck in its own "Tier 2 — write
  after a small upstream contribution") can cite real ids instead of reading `openevo-graph`'s JSON
  informally.
- **CASE crosswalk upstreaming into `conceptbase/alignments/`** — real, valuable content, but has
  no ConceptBase home yet (not built) and is out of scope here per the design note's own §9.5
  sequencing (step 5, only after this migration is verified).

## Relations

- Uses `oe:Concept` (RFC-0002) exclusively — no schema changes.
- All 9 entries are `skos:related` to each other (never to entries in other vocabularies) — content
  anchors are, by design, a self-contained hub structure; cross-vocabulary alignment (e.g. to
  `BIO-CORE`'s `Evolution` concept, which "Ancient Ancestors" clearly relates to) is deliberately
  deferred to `/alignments/` (Phase 2), not asserted here, matching every other vocabulary's own
  practice.
- No alignment yet to `NGSS-LIFE-SCIENCE`/`AI4K12`/the CASE frameworks — same deferred-alignment
  pattern RFC-0007 and RFC-0011 both used; the CASE crosswalk data itself stays in `openevo-graph`
  for now (see "Deferred" above).

## Standards justification

Direct, unmodified use of `oe:Concept` (RFC-0002) and its existing `citations`/`extensions` fields
— no citations exist in the source data for content anchors, so `citations` is simply omitted per
entry rather than populated with placeholders. The one structural question this RFC resolves —
whether content anchors need a new ontology class — is answered "no, they're a tagged `oe:Concept`
subset," on the same grounds RFC-0012 used for cross-cutting themes: no behavior this ecosystem
needs (validation, registry building, relation traversal) actually depends on content anchors being
a distinct type; `extensions["oe:conceptRole"]` is sufficient, keeping this a `content` RFC rather
than requiring `specification-amendment` review.

## ID block reservation

Not applicable — `oe:Concept` ids use the direct-mint `OE-CONCEPT-<vocab-slug>-<code-slug>` scheme
(superseded numeric block-allocation 2026-08-16; see `GOVERNANCE.md`'s Identifier Block Allocation
table). No block to reserve.
